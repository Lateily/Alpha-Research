## 二、你的任务要解决的真实痛点

**这周我们连续踩了同一种坑:申报 ≠ 实物。**

真实案例(全部有 repo 记录,不是假设):
- 一个 PR 自报"四点修订完成",实际有一点根本没进代码;
- 一份文档写"117 条已判分",查账本实际只有 16 条;
- 一个功能自报"新闻链已接入",实测**一条新闻都进不了池子**(字段名写错);
- 一份判定书写"已接入夜链",而夜链里根本没有那个步骤;
- 我(Claude)自己写的检查函数里有 `x == [] or True` —— **一个永远不会失败的检查**,
  然后向 Junyan 报告"全绿"。

这些不是粗心,是**结构缺陷**:没有任何机器在核对"说的"和"做的"是否一致。
六轮人工敌意审计抓出 40+ 个缺陷,但人不可能每天做六轮。

**你的任务就是把这件事变成机器每天自动做。**

## 三、你要交付什么(AIOS-K1 三件)

### K1-a `ai-task.v1` 任务契约 schema
把散在 GitHub Issue、PR 描述、进度板评论里的"任务"编译成**一种机器可读格式**。

必填字段(缺任何一个 ⇒ 状态 `SPEC_BLOCKED`,不许进入执行):
`task_id / title / owner(human) / executor(AI or human) / reviewer /
risk_level(LOW|MED|HIGH|CONSTITUTIONAL) / scope_paths(允许改动的路径) /
acceptance(可验收标准,必须可被机器或人明确判定) / depends_on / status`

交付物:`docs/llm/schemas/ai-task.v1.json` + **正例反例各 ≥3 个**
(反例:缺 acceptance、scope 为空、risk 未声明 —— 必须被 schema 拒绝)。

### K1-b `task_compiler.py` + `registry.py`
- **compiler**:读 Issue/PR/进度板事件 → 产出 `ai-task.v1` 对象;
- **registry**:把这些对象和事件流(CLAIM/UPDATE/DONE/BLOCKED/RELEASE)重放成
  **每个任务的唯一当前状态**。
- 硬要求:**append-only 事件重放**(不覆写历史)、**重放幂等**
  (同样输入跑两次结果完全一致)、**只读**(绝不自动写 GitHub)。

### K1-c `reconciler.py` —— 本任务的灵魂
每天自动比对"账"与"实",输出 `ai_os_reconciliation.json`。必须能抓出六类问题:

| 类型 | 含义 | 我们真实发生过的例子 |
|---|---|---|
| 孤儿任务 | 有 Issue 无人认领无 PR | — |
| 过期 CLAIM | 认领了但超过 expires_at 没动静 | 进度板首条 CLAIM 就漏了过期时间 |
| 无 Issue 的 PR | 代码在跑但没有任务出处 | 多个 |
| **过早 DONE** | 自报完成但验收标准未逐条兑现 | "四点修订完成"实际三点 |
| **DELIVERED_UNWIRED** | 东西造出来了但没人消费 | major_news 采集了但 news.js 零引用 |
| 未消费报警 | 报警产生了但无人处理 | 夜链 INCOMPLETE 旗 |

## 六、你必须知道的一条方法论(本周最贵的教训)

> **每一个自查工具的第一版,都带着它自己要治的那种病。**

本周三次自证:①我写的 preflight 里有永真式检查;②我做的数据迁移只改了外层字段;
③我新建的一致性闸门自己用 `except: continue` 静默跳过损坏文件。

**因此对你的硬要求**:你的 reconciler 交付时,必须先**注入故障证明它会 FAIL**,
再还原证明它 PASS。**一个从没失败过的检查,不配被信任。**
PR 描述里必须贴出这两次运行的真实输出。

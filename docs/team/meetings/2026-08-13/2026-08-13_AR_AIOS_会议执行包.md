## 3. 任务一：今晚完成 GitHub 文件同步

### 3.1 今晚的同步完成定义

只有同时满足以下条件才记为 `SYNC_PASS`：

1. `origin` 明确指向 `https://github.com/Lateily/Alpha-Research.git`。
2. `git fetch --prune origin` 在本人机器上真实成功。
3. 记录最新 `origin/main` 完整 SHA，且与会议 Issue 的远端基线一致。
4. 本地 `main` 通过 fast-forward 更新到相同 SHA；不得带未提交修改更新。
5. 所有正在施工的修改均位于命名分支/worktree，并已 commit + push；不存在只保存在某台电脑的唯一版本。
6. 每个施工分支对应一个 Issue 和一个 Draft/Ready PR，或者明确关闭/退休。
7. `git status --short` 为空；若不为空，必须逐文件说明 owner、用途和计划，不能报 PASS。
8. workspace doctor 至少能够输出结构化报告；环境缺口必须如实保留为 GAP/FAIL。
9. 不创建第二份 clone 来掩盖旧 clone 的问题，不通过 OneDrive/Dropbox 同步 Git worktree。

### 3.2 每个人执行的标准命令

先在本人唯一有效的 Alpha-Research clone 中运行：

```powershell
git remote -v
git status --short
git branch --show-current
git rev-parse HEAD
git fetch --prune origin
git rev-parse origin/main
```

如果当前就在干净的 `main`：

```powershell
git switch main
git pull --ff-only origin main
git rev-parse HEAD
```

如果当前是正在施工的功能分支：

```powershell
git switch <your-branch>
git merge origin/main
```

解决冲突后只暂存明确文件，不使用 `git add .`：

```powershell
git add -- <file-1> <file-2>
git commit
git push
```

然后运行仓库自检：

```powershell
py -3.11 .\scripts\team_ai_workspace.py doctor
```

若机器没有 `py -3.11`，回报 `PYTHON_RUNTIME_BLOCKED`，并给出 `Get-Command python,py` 的输出；不得因此谎报 PASS。

### 3.3 禁止做法

1. Dirty `main` 上直接 pull。
2. 用 `git reset --hard` 或删除目录解决冲突。
3. 用 `git add .` 把本地数据、密钥或无关文件带进提交。
4. 无确认使用 `push --force`；确有 rebase 需要时只能使用 `--force-with-lease`，且先由 owner 说明影响。
5. 把旧 CI、旧 SHA 或截图当作当前 head 证据。
6. 把“文件在本机”写成“已同步到 GitHub”。

### 3.4 统一同步回报模板

每个人在会议 Issue 下粘贴：

```text

OWNER:
GITHUB_USERNAME:

```

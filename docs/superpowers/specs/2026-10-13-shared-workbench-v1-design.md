# 共享研究工作台 V1 规格

状态：REVIEW_REQUIRED；2026-10-13 评审快照；尚未实现或部署。
人类负责人：Junyan。使用者：Junyan、Reed；仅现有获准身份。
本稿修改必须升版本，不能覆盖已用于评审的快照。

## 1. 要交付什么

两人从各自电脑登录同一个私有网址，使用同一后台和共同数据，各自提交研究任务、
生成独立输出；所有任务、输入版本、结果和失败原因统一归档，双方可查询。
正式生产仍只有现有单一写入口。本工作台只读生产文件，不接管夜链、模拟账或批准权。

第一批功能只有 `observe` 与 `snapshot-brief`。后续财报、筛选、深研、技术分析
通过各自执行器和契约验收后再接入，不以本稿替代其授权。
“接真实生产数据”不等于“工作台获得生产写权限”。

## 3. 架构与边界

```text
Junyan 浏览器 / Reed 浏览器
  -> 既有 Tailscale 私有 HTTPS / 身份校验
  -> 工作台 API
       -> 个人工作区 + 团队只读查询
       -> 持久任务队列 -> 最多 2 个只读任务执行槽
       -> 单个只读同步器 -> 冻结输入仓
       -> 共享 SQLite 事件记录 + 独立工件目录

既有 ar-live -> 固定白名单只读读取 -> 工作台冻结输入仓
工作台 -> ar-live 写入：禁止
```

复用 Python 标准库、SQLite、现有 React/Vite、现有证据与简报校验器。
不增加云资源、外部队列、数据库服务或模型依赖。
同一 state_root 仍只有一个服务持有 lifetime lock；两个执行槽不是两个生产 writer。
浏览器不直连市场/模型 API，不提供任意路径、命令、URL、SQL、provider 或权限参数。

主机及服务 UID 是信任边界；不声称抵御主机管理员或同 UID 恶意进程。
模型输出归档不是自动训练，也不自动修改研究规则。

## 4. 个人工作区

每个获准登录身份由服务端分配持久、不可变的 workspace_id。
磁盘目录使用服务端生成的 ID，不用邮箱、用户输入或查询参数拼路径。
actor 来自已验证的 Serve 登录身份；客户端不能指定 actor 或 workspace_id。

页面提供三个视图：

- 我的任务：本账号的任务、历史输入、执行状态、结果与失败原因。
- 团队结果：两个获准账号的任务及已封存输出，可查看、下载、比较，不可覆盖。
- 共同数据：最新尝试、最后成功发布、当前采用的冻结快照及各模块来源身份。

两人同等获得研究访问权限；OWNER 标签不等于方法、U4 或 paper 批准。
V1 的个人空间是任务归属和写隔离，不承诺对获准同事隐藏内容。
个人草稿编辑、在线审批、白名单管理页面均不在本批范围；现有白名单继续由 Junyan 管理。
不得把未知历史 actor 推定为任何人；显示 LEGACY_UNATTRIBUTED，只读保留。

任务元数据至少包含 job_id、workspace_id、actor、kind、输入 hash、源 run_id/交易日、
提交时刻、执行代码 SHA、schema 版本、状态、attempt_id、输出 hash 和安全错误码。
所有新研究工件为 WORKFLOW_DEBUG，human_review=PENDING，生产及交易权限为 false。
双方查询可看同一输出，但改分析须开新任务并引用旧结果，原件保持不变。

## 5. 输入绑定与共同数据

输入分为两层：

1. 发布快照：指针、manifest、白名单模块和 bundle 的冻结原件，按内容去重。
2. 尝试观察：nightly_run 的安全字段投影；保留自己的 run_id、交易日、时刻和原文件 hash。

输入封套引用上述两层，形成确定的 input_hash。提交任务时冻结封套。
最新失败尝试不得取代最后成功发布；公开展示和该任务使用的输入也分别显示。
排队期间出现新发布，只更新共同数据视图，已提交任务仍使用原 input_hash。
请求只可选择服务端已有 snapshot_id，不可传入源文件路径。
没有可用冻结发布时拒绝简报请求，显示精确阻断，不退回合成输入或旧试用包。

代码版本和输入不同，结果不要求相同；同输入、同执行代码生成的确定性报告字节应相同。
报告正文不嵌入 actor/job_id；它们写在任务封套，因此不同用户回执可不同，报告 hash 可一致。
报告与引用来自冻结原件，不声称已核验发行人原文。

## 6. 任务并发与恢复

新行为必须通过独立、默认关闭的共享工作区运行模式启用。
旧本地模式和既有私有简报模式的请求、状态及回执保持兼容；不偷偷升级运行库。

### 6.1 提交与执行

- 提交持久记录后返回 202 与 job_id，不在 HTTP 请求内等待渲染。
- 正常小型夹具的提交响应目标为 2 秒内；没有冻结输入则明确拒绝。
- 请求身份、类型、输入先校验；同账号同 command_id 同请求返回原任务。
- 同 command_id 换内容或换账号为 409，不启动第二次执行。
- 同一时刻最多 2 个任务执行，队列 FIFO；每账号最多 2 个未终结任务，全局最多 20 个。
- 超额返回 429；用户能看到排队和限制，不丢任务、不无限开线程。
- 状态为 QUEUED、RUNNING、SUCCEEDED、STOP、INTERRUPTED、RECOVERY_REQUIRED。
- SUCCEEDED 只表示渲染和结构/哈希核验完成，不能表示研究质量或人工核验通过。

认领使用 SQLite 事务和唯一 attempt_id/代际 token；终态提交须核对当前 token。
只读渲染子进程只得到冻结输入与本 attempt 输出目录，不得到生产根、数据库或凭证。
每个 attempt 的硬超时为 120 秒；超时终止该进程组，落 STOP，不占用执行槽或拖住另一人。
异常记录安全错误码和有限步骤，不保存环境变量、完整请求、原始传输异常或密钥。

### 6.2 提交点与恢复

工件在 attempt 独立暂存目录生成，重开校验后形成不可变结果封印。
数据库中的唯一终态提交才让结果对用户显示为成功；未提交目录只是可恢复证据。
workspace_events 仍 append-only；队列技术状态可事务更新，但不能修改旧审计事件。

服务重启必须先获得同一把 lifetime lock，检查代码/schema 兼容，再恢复：

- QUEUED 且版本兼容：继续排队，保留原输入和任务身份。
- 输出已封印、绑定正确但终态未提交：重开验证并收敛，至多一条终态，不重渲染。
- RUNNING 无完整输出：旧 token 失效；仅本批只读、冻结输入任务允许一次自动恢复。
- 同一 job 总计最多 2 个 attempt；再次中断为 INTERRUPTED，不无限自动重试。
- 工件矛盾、输入损坏、代码/schema 不兼容：RECOVERY_REQUIRED，不能用新代码或新输入补跑。
- 旧版本 STARTED 无足够绑定：INTERRUPTED / LEGACY_NOT_RECOVERABLE，不推测成功。

旧 worker 即便晚到，也只能写自己的 attempt 目录，不能提交当前任务终态。
网络断线只使浏览器重新查询原 job_id，不取消、复制或自动重提任务。
STOP 后重复原请求返回原 STOP；新尝试需要新 command_id 并保留原失败。
不承诺分布式 exactly-once；此处是单主机单协调器下的唯一终态和有限安全重执行。

## 7. 生产数据只读自动同步

共享 V1 的只读同步器独立于原调度器，不能启用市场采集、paper、模型或夜链任务。
启用参数必须显式配置；启动时检查一次，随后每 60 秒检查一次。
只在指针/尝试身份变化时处理，不因轮询时刻变化重复封存相同发布。
主机休眠或离线期间不保证更新；恢复后读取当前最新发布，不声称已补全错过的每一轮。

一次发布导入：

1. 读取指针原件，检验 run_id、交易日、manifest 路径与 hash。
2. 只读取现有 PUBLIC/BUNDLE 白名单，不跟随链接，不打开生产 SQLite 引擎或读取凭证。
3. 校验各读取模块的指针 hash、run/date 绑定、bundle 覆盖和哈希。
4. 原件复制到隔离暂存，重开验证；再次读取指针，确认整个捕获期间未切换。
5. 封印原件和来源 manifest，再事务登记为可用快照；此后才改变工作台当前快照。

当前观察器仅有子集验证能力，新实现不得直接把 publication_verified 改成 true。
封套必须明示验证白名单和范围 SCOPED_SNAPSHOT_NOT_FULL_NIGHTLY_ACCEPTANCE。
24 步、双指针、全 manifest 的完整生产验收仍独立；若未核验就标 NOT_EVALUATED。
读取工件的 hash/身份矛盾阻断该快照；文件结构合法但质量缺数保留 DATA_BLOCKED/PARTIAL。
不能因 Macro 缺预期差把它补成 0，也不能因运行 COMPLETE 把六维或 NAV 缺数补绿。

捕获遇到指针切换为 SOURCE_CHANGED，弃用未提交暂存；下一个轮询重新检查，禁止现场改源。
缺 manifest、权限拒绝、损坏或容量不足显示同步失败并保留上次好快照及其明确日期。
显示 last_checked_at、last_successful_sync_at、current_snapshot_id、source_run_id 与安全错误码。
正常固定验收数据下，新发布到两端可见的目标上限为 120 秒；前端任务状态轮询为 5 秒。
前端网络错误必须显式显示断线/旧状态，不能无限保留绿色“正在同步”。

每文件仍按现有 12 MiB 上限；现有 100 个观察、10000 个事件等容量门不能静默绕开。
去重后到容量门时显示 CAPACITY_BLOCKED，不删除历史；扩容/归档另走可审查迁移。
V1 不承诺永久无限存储。

## 8. 权限、迁移与运行边界

保留准确 Host/Origin、身份绑定 cookie、重复头/字段拒绝与白名单校验。
只对当前两名获准成员开放；不增 tailnet 用户、ACL、公开端口或新人权限。
任何用户均不得借队列、恢复、同步器或输入选择绕开已有 U4/paper/付费/部署拒绝门。

新状态 schema 要显式版本化。隔离库升级前用 SQLite backup API 制作一致备份，
验证 integrity_check、审计行数/链尾、工件 hash 和 scratch restore。
迁移事务崩溃须能收敛；不修改老事件正文、未知 actor 或历史工件。
旧二进制拒绝打开新 schema；回退新界面不等于把旧备份覆盖新任务。

新实现先在未占用端口和全新隔离 state_root 做测试，不替换在用服务。
同一最终 HEAD 通过本地全套、远端 Python/UI CI、独立复审后，才做共享试运行部署验收。
部署/入口切换需明确批准；本次落盘不替代批准合并、切服务或改生产。
实际两机测试须保留已有隔离任务，不覆盖旧库。不能把本机两个浏览器当成两台电脑。
Mac 仍须开机联网；本批不新增 launchd、云常驻、自动停旧生产或外部备份上传。

## 10. 验收与完成定义

验收矩阵见 `docs/team/SHARED_WORKBENCH_V1_ACCEPTANCE.md`。
所有条目初态 NOT_RUN；真实账号、地址、凭证与运行原件只保留在获准本地证据目录。

完成须同时满足：

- 同一最终代码 HEAD 的全量离线套件、变异门、远端 Python/UI CI 和独立复审通过。
- 新增行为覆盖正常、缺失、矛盾、历史版本，崩溃测试覆盖每个持久写入点。
- Junyan Mac 与 Reed Windows 实际同时提交独立任务，双方核对同一冻结输入与结果。
- Windows 独立回传 job_id、报告 SHA256 与具名接收回执，不由 AI 代填。
- 自动导入新的真实发布，两端明确展示最新尝试/最后发布/当前快照，不用旧轮补绿。
- 正式源无本工作台写入；所有研究仍 WORKFLOW_DEBUG、人工核验 PENDING。

只完成代码是 CODE_READY；只有本机浏览器证据是 LOCAL_QA_PASS；
两端真实验收缺件时必须保留 TWO_DEVICE_PENDING，不能声称多人生产已交付。
正式前瞻 paper 闭环、研究质量、稳定夜链样本期不是这次共享工程的完成声明。

## 11. 本稿自检记录

- 目标、已有能力和待建能力分开，未把 Draft 或本机试跑说成已上线。
- “自动同步”仅是生产文件只读导入，不是自动采集、双写、付费调用或学习改规则。

- 快照内容去重与轮询时刻分离；排队、恢复均绑定同一输入与代码版本。
- 恢复上限、容量门、主机离线与旧版迁移结果均明确，不无限重试或无限存储。
- 跨模块反例及真实 Windows 回执在验收清单中单独列出。

不是买卖指令；研究信号，human executes。
